### 1. Reality inventory

**Real, working, tested.** 1,633 backend tests across 79 files, CI green.

- **Energy engine** — `bmrEngine.js` (37 KB). BMR = mean of applicable formulas, TDEE = BMR ×
  occupation multiplier + training kcal/day, target = TDEE − rate×500 floor-clamped. 36-occupation
  table, per-formula exclusion toggles. Genuinely rigorous.
- **Adaptive expenditure** — `expenditureEstimator.js` (36 KB) + `adaptiveTarget.js` (20 KB).
  Reconciles logged intake against observed weight change to estimate *measured* TDEE, then walks
  the applied target at ±125 kcal per weekly cycle with the safety floor outranking the cap
  (`adaptiveTarget.js` :192–213). 12 weekly checkpoints (`LEDGER_WEEKS = 12`). **This is the best
  thing in the codebase and it is nearly invisible in the product.**
- **Solver** — `mealSolver.js` + `weeklyPlanner.js` (64 KB). Week solves in 1–15 ms on the real
  pool. Honest infeasibility diagnosis; never silently misses a target; never suggests loosening an
  allergy.
- **Exclusion gate** — `exclusionGate.js` (16 KB). One implementation of "may this user see this
  recipe", four evidence sources (ingredient rows *with* persisted allergen metadata, importer
  prose, recipe title, full step text), fails closed on degraded input, and a test that scans `src/`
  and breaks the build if a new surface reaches around it. This is better than most funded apps.
- **Data** — 14,122 foods / 889 recipes in SQLite, fiber-adjusted Atwater validator with documented
  exemptions, per-row provenance (USDA-VERIFIED / LABEL / AI-ESTIMATED).
- **Recipe importer** — schema.org JSON-LD → ingredient-line parser → resolve to validated food DB.
- **Training** — v1 templates only. `generator.js` produces 4 weeks that are byte-identical
  (`:131–151`). No progression tracking.
- **Brain** — ~35 files under `src/lib/brain/`. Governed LLM layer with a cost ledger, injection
  guard, per-user budget. **Default OFF** (`brain/index.js` :2–4; `server.js` :21 makes an absent
  relay config equivalent to never having the feature).

**Scaffolded, code-complete, not yet live.** The whole subscription layer:
Supabase Google auth, `requirePremium` on 17 endpoints, Lemon Squeezy checkout + webhook state
machine with 19 tests driving the real route, Postgres migration pipeline, Railway Dockerfile,
`flipPremium` / `flipPremiumCloud` test tooling. Server-half gating is **proven live** against real
HTTP (BUILD_PLAN Stage 2). What's missing is entirely dashboard clicking: Supabase project, Google
OAuth client, LS store, Railway deploy.

**Aspirational.** The `roadmap/` directory (Sentry, mobile packaging, legal). The fridge solver.
The LP portion solver. Anything in the phase log dated before 2026-07-24 (`CLAUDE.md` carries its
own table of superseded claims — an unusually honest artifact).

**The gap between docs and code is small and self-policed.** That is rare and it is the reason this
audit could be done in an afternoon. It is also the tell for the failure mode in Q8.

### 3. Cost model — LLM inference per active user per month

Production LLM call sites, traced from the routes:

1. `POST /api/recipes/generate-drafts` → `aiRecipeClient.generateRecipeDrafts` →
   `model = MODELS.escalation` = **`claude-opus-5`** (`aiRecipeClient.js:203`, `brain/config.js:22`),
   `DRAFT_MAX_TOKENS = 8000` (`:188`), `thinking: {type:"adaptive"}`, `effort: "high"` (`:238–239`).
2. Solver AI fallback (`mealSolver.js` :754–806) — gated by `isBrainEnabled()`, **off by default**.
3. `/api/brain` chat — mounted but "inert with BRAIN=off" (`server.js:132`).

So on the hosted web product **only #1 bills**, and only if `ANTHROPIC_API_KEY` is set on Railway —
which `BUILD_PLAN.md` Part C step 2 makes explicitly optional.

Arithmetic (rates verified 2026-08-06: Opus 5 = $5/MTok in, $25/MTok out — the repo's `pricing.js`
table is accurate):

```
input   12,000 tok  (EST_INPUT_TOKENS_PER_TURN, pricing.js:42)  × $5/1e6  = $0.060
output   4,000 tok  (typical, of an 8,000 cap incl. thinking)    × $25/1e6 = $0.100
                                                        typical  ≈ $0.16 / generation
output   8,000 tok  (cap)                                × $25/1e6 = $0.200
                                                            max  ≈ $0.26 / generation
```

Caps in force (`brain/config.js` :27–45):

| Cap | Value | Generations it buys |
|---|---:|---:|
| Per request | $0.50 | never binds |
| **Per user / month** | **$5** | ~31 |
| **GLOBAL / month** | **$15** | **~94, across every user combined** |

**This is the finding.** The global cap is calibrated for one person — the owner — and does not
scale with revenue. At 3 subscribers each using their full per-user allowance the global budget is
gone. At 50 subscribers, every customer gets **1.9 AI recipes per month** before the app tells all
of them "AI generation paused." A paid feature that silently converts to a deterministic fallback
across the entire customer base is worse than not shipping it.

**Cost per active user per month: $0.00–$1.60 depending on usage, hard-capped at $5/user and
$15 total.** Inference is *not* the constraint on pricing. Unit economics at $24.99/mo (Lemon
Squeezy is Merchant of Record, 5% + $0.50 → net $23.24):

```
net revenue                    $23.24
LLM (10 generations)           −$1.60
Railway hobby                  −$5–20 / month TOTAL, not per user
Supabase                       $0 free tier → $25/mo Pro
                        gross margin ≈ 93%, break-even ≈ 2 subscribers
```

Fine. The economics are not the problem. **The economics are so forgiving that they hide the real
problem, which is that nobody is going to pay.**

### 4. Safety audit — independent verification of the math

I checked the three things the builder says are product-killing.

**Calorie floors — CORRECT, and enforced at three layers.**
`bmrEngine.js:224` `effectiveFloor()` = `max(sexFloor, round(rmr × 0.95), profile.floorKcal)` with
`SAFE_FLOOR = {M: 1500, F: 1200}` at `:216`. The RMR×0.95 term was a real fix — without it a
high-RMR user at an aggressive rate could be prescribed ~450 kcal below the documented minimum.
`deriveTarget()` at `:230` clamps and reports `floored: true`, `achievableRate`, so the UI can say
"you'll lose about X, not the Y you picked — add movement, not less food" (`:261`). The adaptive
layer re-derives through the same `deriveTarget()` (`adaptiveTarget.js:173`), and the ±125 step cap
is explicitly subordinated to the floor (`:192–194`, `:212`). **I could not construct an input that
produces a sub-floor prescription.**

**Dangerous targets — REFUSED, not warned.** Goal-BMI below `GOAL_BMI_REFUSE` is a hard refusal;
between that and `GOAL_BMI_ACK` requires explicit acknowledgement (`routes/profile.js:386`,
`SetupWizard.jsx:90`). Under-18 is refused outright (`ADULT_MIN_AGE`). Rates over 1% body weight per
week require `rateAcknowledged: true` **in that request** and 422 otherwise, with `ack` naming
*which* confirmation is being asked so a client can't answer the goal-weight gate with a rate
acknowledgement (`profile.js:468–474`). There is a SCOFF-based eating-disorder screen
(`WellbeingCheck.jsx`) with verified Canadian crisis resources — NEDIC's weekend closure was
corrected in `lib/wellbeingResources.js` because a wrong hour sends someone in crisis to a dead
line. **This is more careful than any commercial app I know of.**

**Allergy exclusion — STRUCTURALLY SOUND, with one live hole.** `exclusionGate.js` is the right
design: the gate owns the evidence (you cannot hand it a weakened view of a recipe), a degraded
recipe fails *closed* (`:162`), and a source scan breaks CI if a new surface imports the raw
primitives. Full step text is treated as evidence and negation parsing was deliberately rejected
because "add butter, or omit for a dairy-free version" contains a negation and still cooks butter
in. Over-blocking is the chosen failure direction. Correct.

**The hole:** the AI-generation path carries a per-generation user-toggleable allergen override
(Phase 5 log — "allergen override rebuilt as a loud red per-generation checkbox that auto-resets").
Loud and auto-resetting is good UI. It is still a path where a shellfish-allergic user can, in two
clicks, receive a shellfish recipe from a system whose entire safety story is "the weak path is
unreachable." On a free desktop app for one person that is a defensible choice. On a paid product
serving strangers it is the single largest liability surface in the repo. **Recommendation: on the
hosted web product, remove the override entirely.** It is one boolean.

**Second hole, non-safety but corrosive:** `scripts/scanSecrets.mjs:84` returns early on any file
containing a NUL byte, and `dietaryFilter.js` — the allergen vocabulary, 122 KB, the most
safety-critical source in the repo — contains 3 NUL bytes. It is therefore permanently exempt from
the secret scan, and `tests/scanSecrets.test.js:50` **asserts that the skip is correct**, so a green
suite defends the exemption. Recorded in `CLAUDE.md`, never fixed.

## STAGE THREE — THE TEARDOWN

### Q1. The ChatGPT objection

**Strongest form of the objection, stated fairly:** *"ChatGPT writes me a 7-day meal plan hitting
180 g protein at 2,100 kcal, in ten seconds, for free, forever. It adapts when I ask. It knows
recipes I like. It's on my phone already. Why is a web app from a stranger worth $300 a year?"*

That objection defeats most of this product. Here is what survives it, in descending order of how
much it actually survives:

**1. Persistent measured state — the only one that is structurally impossible in chat.**
`expenditureEstimator.js` reconciles logged intake against observed weight change over a rolling
12-week checkpoint ledger and produces *your measured expenditure with a confidence band* — then
`adaptiveTarget.js` walks the applied target toward it at ±125 kcal/cycle. A chat interface has no
weigh-in series, no intake series, and no mechanism to change its own prior. You can paste your
weights in every session, but you are then the database, and the moment you stop pasting, it stops
knowing. **This is not "ours is better." A stateless interface cannot hold a longitudinal
posterior.** It is the answer.

**2. Enforced allergy exclusion.** `exclusionGate.js` fails closed and cannot be talked out of it.
An LLM forgets a constraint stated 40 turns ago; this is a documented, universal property of long
contexts, not a model-quality issue. For shellfish/gluten/soy this is the difference between an
inconvenience and an ER visit.

**3. Arithmetic that is reconciled rather than asserted.** ChatGPT states macros. This computes them
from a validated food row and *scales grams* until the day lands in tolerance
(`weeklyPlanner.scaleRecipe`, `foodValidation.js` fiber-adjusted Atwater ±15%).

**Concession — and it is large.** #2 and #3 are safety and correctness properties. **Nobody shops on
correctness they cannot verify.** A prospect cannot tell your reconciled 2,097 kcal from ChatGPT's
asserted 2,100 without redoing the work, and if they could do that they wouldn't need either of you.
So #2 and #3 keep users; they do not acquire them. Only **#1 acquires** — and only if you can make
someone *feel* the difference between "a formula's guess about people like you" and "a measurement
of you." Today the app does not attempt that. It is a number on the Engine tab.

**Verdict: the objection is answerable, with exactly one answer, and the product currently does not
say it.**

### Q2. The nine-day problem

**Architecturally, nothing creates day 30. I want to be precise about how nothing.**

There is no scheduler, no queue, no cron, no worker, and no email provider anywhere in
`backend/package.json`. Nothing in this system can execute at a time the user did not personally
initiate. **The application is incapable of contacting a user who does not open it.** That is not a
missing feature; it is a missing organ.

The one real habit loop that exists is: *weigh in → target changes → plan changes.* That is a
genuine variable-reward feedback loop and it is better than a streak counter. But it is entirely
pull. It fires only if they open the app, and by day 9 they have stopped.

Worse, the loop's payoff is **back-loaded past the danger zone**. The adaptive layer needs roughly
two weeks of weigh-ins before `adaptive.applied` flips true. So the product's single differentiating
moment arrives *after* the median diet-app user has already churned.

**Design it, then:**

| Day | Fires | Channel | Why this and not something else |
|---|---|---|---|
| 0 | Signup → first solved day in <5 min | in-app | Time-to-first-value is the only day-0 metric |
| 1 | "Did you eat yesterday's plan?" one tap | in-app + email | The `ate-as-planned` toggle already exists and is idempotent server-side |
| 3 | First weigh-in nudge | email | Without weigh-ins the whole engine is inert |
| 7 | First trend point + **"3 more weigh-ins and this stops being a formula and starts being you"** | email | Names the payoff and dates it. This is the retention line. |
| 14 | **Adaptive flips on.** "Your body burns 2,740 — the textbook said 2,510. We were wrong about you by 230 calories a day." | in-app celebration + email | This is the product. It has never been surfaced as an event. |
| 21 | Weekly digest: trend, adherence %, next week's target | email | |
| 30 | "Here's what a month of measuring you looks like" — the exportable artifact | email | The thing they'd lose |

Every row past day 1 requires email. **Email is the #1 build item in this entire document.**

### Q3. The moat, scored

| Candidate | Backed by | Defensibility | Why |
|---|---|---|---|
| **Measured-expenditure history** | `Weighin` + `MealLog` + 12-week checkpoint ledger | **7/10** | Takes 12 weeks of *their* discipline to rebuild anywhere. Genuinely compounding. Capped at 7 only because `LEDGER_WEEKS = 12` means it plateaus — after ~3 months an extra year adds little. |
| Learned taste / adherence | `RecipeRating`, `recipeTaste.js`, `tasteTier` | 4/10 | Real but shallow today — ratings are explicit, not inferred from what they actually ate. Would score 7 if driven off the diary. |
| Allergy + dietary config | 10 checkboxes + `excludedFoods` | 3/10 | Re-enterable in 90 seconds. |
| Saved plans / cart / grocery lists | `Plan`, `PlanSlot`, `GroceryList` | 2/10 | Disposable by nature — a meal plan's value expires in a week. |
| Training history | `TrainingPlan` → … → `TrainingExercise` | 2/10 | Regenerate replaces transactionally; there is no logged-performance history to lose. |
| Social | — | 0/10 | Does not exist. Correctly. |

**Strongest: measured expenditure, 7/10.** It is the only asset where leaving costs *time* rather
than *typing*.

**And you have deliberately drilled a hole in it.** The constitution says "Data is never trapped:
JSON+CSV export must always work," and `routes/export.js` (53 KB — the largest route file in the
repo) honours that, ungated, on the free tier. That is the right call ethically and I am not asking
you to reverse it. But be clear-eyed: **your strongest moat is one button away from portable.** The
defensibility is not the data; it is that no competitor can *ingest* it usefully. Keep it that way
by making the value live in the interpretation, not the rows.

### Q4. Feature or company?

Going through them one at a time, against products shipping today:

**Fridge-constrained solver** — does not exist (§0). Cannot be a differentiator. If built:
MacroFactor could ship a pantry filter in a quarter; a filter over an existing recipe pool is not
hard. **Copyable.**

**Coaching without logging** — this is MacroFactor's *headline feature*. Their entire marketing is
"adaptive TDEE, no more guessing," at $11.99/mo or $71.99/yr. You are not differentiated here; you
are at **parity with the category leader, at 2× the monthly price, with no brand.** Your
implementation may well be better — the step cap, the floor-outranks-cap rule, and the drift
reconciler are more careful than most — but "better in ways the buyer cannot evaluate" is not a
market position. **Already shipped by a competitor.**

**Per-number provenance** — Cronometer shows data source per nutrient today and has for years. Your
version is more granular (USDA-VERIFIED + FDC id / LABEL / AI-ESTIMATED, never silently mixed) and
the five-formula BMR display is genuinely novel. But it is a display layer over public data.
**Copyable in weeks.**

**Say the word: this is a feature set, not a company.** Every individual capability is inside a
funded competitor's one-quarter roadmap.

**The honest reframe, which is not a consolation prize.** What a competitor cannot copy in a quarter
is the *combination under a safety constitution*: no red on food data, floors that are shown rather
than hidden, an exclusion gate that fails closed, an ED screen that is never gated, and a refusal to
prescribe below the line. MyFitnessPal will not ship that because it conflicts with engagement
metrics. That is a **positioning** advantage — "the diet app that will tell you no" — not a
technical moat. Small businesses are built on those. $10M companies are not.

### Q5. Reasons not to pay, and reasons to cancel

**Declines, ranked by expected frequency:**

1. **Free is good enough.** MyFitnessPal free + ChatGPT covers 80% of the perceived job.
2. **No reason to trust the numbers.** An unknown solo brand telling you what to eat, with zero
   reviews, zero press, zero social proof. The math being *actually* right does not help until
   someone believes it.
3. **Price.** $24.99/mo is above MyFitnessPal Premium ($19.99), 2× MacroFactor ($11.99), 2.8×
   Cronometer Gold ($8.99). You are the most expensive app in the category and the least known.
4. **"I'd have to cook these."** Every plan assumes cooking from a recipe. A large fraction of the
   market eats restaurant/prepared food and the product has no answer for them.
5. **The pool doesn't match how I eat.** 889 recipes sounds like plenty until filters apply — the
   Phase 4 log records the vegan pool at **51 recipes**, and the app honestly says so. Honest and
   fatal in the same breath.
6. **It's a website.** A Vite SPA in mobile Safari, no app-store presence, no home-screen icon.
7. **Can't evaluate it.** Free tier = targets + workouts + *unportioned* recipe browsing. The thing
   you're selling is invisible until you've paid.

**Cancels in month 2, ranked:**

1. **Stopped opening it.** No mechanism exists to intervene. This will be the plurality cause by a
   wide margin.
2. **Stopped cooking the plans.** Plan-vs-reality divergence, and the app can't tell — the diary
   picker only accepts **grams** (UX review open question #3), so logging a burrito means guessing
   its mass. Nobody does that twice.
3. **Goal reached, or cut abandoned.** Structural: this is a *cut* product. Cuts end. There is no
   maintenance mode, no bulk mode, no reason to still be here in month 5.
4. **Recipe fatigue.** Variety cap is 2×/week over a filtered pool that may be dozens of recipes.
5. **Weight stalled and the explanation didn't land.** The engine handles this correctly; the UI
   does not narrate it.
6. **Found MacroFactor.** Half the price, App Store, thousands of reviews.

**#3 deserves its own line: churn is designed into the positioning.** A cutting app has a
built-in end date. Every subscriber is on a timer you set.

### Q6. The wedge audit — beginners is wrong

**The evidence against beginners:**

- **The product is a precision instrument and every screen shows it.** `EngineTab.jsx` displays five
  BMR formulas and their mean. `ProfileTab.jsx` (58 KB) exposes a 36-occupation table with manual
  multiplier override, per-formula exclusion toggles, `rateLbPerWeek`, and a stricter-only
  `floorKcal`. The 2026-08-02 UX review found Profile is ordered by *Prisma column order* and "Rate
  of loss — the one dial a cutter turns — sits at y=732," i.e. below the fold.
- **Onboarding is four steps with two refusal gates.** `SetupWizard.jsx` `STEPS` = Units & stats /
  Activity / Diet / Rate of loss, plus a minor refusal and a goal-BMI refusal that a beginner
  entering an aspirational goal weight will hit and read as rejection.
- **Beginners are the worst commercial segment in this category**: most price-sensitive, highest
  churn, best served free, and the one segment where an ED-adjacent user is most likely to appear.
- **The prompt's own premise concedes it**: "beginners don't want precision; they want to be told
  what to eat." Correct. And the thing this app is *uniquely* good at — showing you the derivation
  of every number — is worthless to someone who doesn't want the derivation.

**The correct wedge:**

> **Men 28–45 in a deliberate 8–16 week cut, who have already tracked macros in MyFitnessPal, and
> are sick of logging every meal.**

Why this one:

- They already believe in macros, so you skip the entire education problem.
- Logging fatigue is a *felt, nameable pain* — you can write the headline in one line.
- They are not price-sensitive: this cohort buys creatine, whey, sleeves, and $200/mo coaches.
- They have a deadline, which means high day-30 intent.
- **They are the person the app was already built for.** It was built for Shad.

**Messaging, and the channel that costs nothing.** Do not lead with the engine. Lead with the
builder. Construction by day, built this at night because he was sick of weighing chicken at 5 a.m.
before a 10-hour shift. That story is true, it is checkable, it converts in exactly the communities
this cohort lives in (r/fitness30plus, r/leangains, r/gainit, r/xxfitness for the parallel segment),
and it costs $0. The *blue-collar shift-worker* angle is the **voice**, not the segment definition —
narrowing the segment to blue-collar makes it too small to reach; using it as the voice makes the
whole segment trust you.

### Q7. Trust and liability

**Exposure, in order of severity:**

1. **Allergen incident via the AI-generation override.** The one path where a user-facing toggle can
   defeat the exclusion gate. On a paid product serving strangers this is the sharpest edge in the
   repo. **Remove it on web.** One boolean.
2. **ED-adjacent user.** Substantially mitigated: floors that refuse rather than warn, a minor gate,
   a goal-BMI refusal, an always-visible SCOFF screen with verified crisis numbers, and a color law
   forbidding red on food data. This is better than the category. It is not zero — no software
   prevents someone from lying about their weight.
3. **Unauthorised practice.** In Alberta, "dietitian" and "nutritionist" are protected titles under
   the *Health Professions Act*. Giving general nutrition information is not restricted practice.
   You are fine **as long as you never imply clinical credentials or treatment.**
4. **Data.** PIPEDA applies. You hold health data (weight, body fat, eating-disorder screen
   responses). The privacy draft acknowledges this; it is a draft with `[BRACKETED]` placeholders.
   **And you cannot delete an account** (§2). That is a live compliance and ethical problem.

**Missing guardrails to close before charging:** ship `DISCLAIMER.md` (it currently never ships),
fill the legal placeholders, put the medical disclaimer on the paywall page as well as the sign-in
card, add account deletion, and remove the allergen override on web.

**Never claim, in any marketing copy, ever:**

- "Clinically proven", "medically approved", "doctor-recommended", "designed by dietitians"
- "Nutrition advice", "meal plan prescription", "treatment" — call it *information* and *planning*
- "Safe for diabetes / pregnancy / PCOS / any condition"
- "Guaranteed results", "lose X lbs in Y weeks", any specific outcome promise
- Before/after photos implying typical results
- "Accurate" without qualification — say "shows its work" instead, which is both true and better

### Q8. The solo-founder failure mode

**Named: he will keep building, because building is the part he is good at and selling is the part
he is not. The repo is the evidence.**

- 1,633 tests across 79 test files
- 21 local branches
- A 10-stage / 169-finding systems audit (41 files)
- A 10-reviewer UX audit (13 files, 250 KB)
- A 25-agent solver deep-dive, then a 10-agent follow-up that reversed 5 of its claims
- A 9-phase design overhaul, then a *second* design direction (SIGNAL BLACK) superseding the first
- **Zero paying customers**

That is an extraordinary amount of high-quality work pointed almost entirely inward. And the pattern
is self-similar: the UX audit produced a 22-item ranked backlog whose #1 item is a **one-line fix**
that is still unapplied four days later, while a whole new Postgres migration pipeline shipped in
the same window. The infrastructure is easier and more satisfying than the one line that would make
the product's numbers agree with each other.

**The second-order version:** 20 hrs/week on top of 10-hour construction days, with no revenue
signal, is sustainable for about six months on enthusiasm and then it isn't. The specific danger is
that the *first* revenue signal — three signups, then silence — reads as failure and triggers a
retreat into the backlog, where progress is legible and immediate.

**Design around it, concretely:**

1. **A single gate on the Now phase: does this change move a stranger closer to paying?** If no, it
   waits. Written down, checked weekly.
2. **Ship the 20-stranger test (§Stage 4) before writing another feature.** It is the only thing in
   this document that produces information you do not already have.
3. **Cap non-revenue work at 4 of the 20 weekly hours** during the Now phase.
4. **Kill the modules named in Stage 5, out loud, in the repo.** Unkilled optional work is a standing
   invitation to drift.

### The panel disagreements, in writing

Consensus would mean I flattened this. Four real splits:

**A. Dietitian vs. Retention Operator — the free tier.**
*Dietitian:* the safety layer (floors, ED screen, honest refusals) is the most valuable thing here
and must never sit behind a paywall; the current split already gets this right and Wellbeing is
correctly never gated.
*Operator:* free targets + free workouts + free browsing is too generous. A user can get the
calorie number, the macro split, and a training plan for nothing — that is most of the perceived
job. There is no reason to convert.
**Adjudication: Operator wins on scope, Dietitian wins on the line.** Safety and the ED screen stay
free forever, non-negotiable. But *training* should not be free — it has nothing to do with safety
and it is a whole second value prop given away. Move Training behind the paywall. Keep targets free
(they are the hook that proves the math) and keep export free (constitution).

**B. Product Designer vs. Systems Engineer — what to fix first.**
*Designer:* the UX review's Tier-1 list (30 uppercase eyebrows, five copies of the target number on
one screen, 11 Shift+Tabs to get back to nav) is why nobody will stay; visual noise is the churn
driver.
*Engineer:* none of that matters if the app shows 208 lb and 206.5 lb for the same statistic. A
user who spots that once never trusts a number again, and the whole positioning is trustworthy math.
**Adjudication: Engineer.** Correctness precedes polish, and the fix is one line versus ~30. But the
Designer's #8 — stripping the eyebrow prop from ~30 call sites — is the highest ratio of
perceived-quality gain to hours in the entire backlog and should go in the same week.

**C. Skeptical Buyer vs. everyone — is this worth continuing at all.**
*Buyer:* it is a feature, the category leader ships the differentiator at half the price, the
segment churns by design because cuts end, and the founder has 20 hrs/week and no budget. The
rational move is to stop.
*Operator + Designer:* the code is done, the marginal cost of finding out is two weeks and $0, and
the downside is bounded.
**Adjudication: the Buyer is right about the ceiling and wrong about the decision.** This will not
be a venture-scale company; nothing in this document should be read as saying otherwise. But
"$500–2,000/month from 40–150 people who genuinely need it" is a real outcome, it is worth ~$6–24k a
year against an Edmonton cost of living, and the remaining cost to find out is measured in hours,
not dollars. **Proceed — with the ceiling stated honestly up front so that 40 customers reads as
success and not as failure.**

**D. Dietitian vs. Skeptical Buyer — the AI allergen override.**
*Buyer:* it is a documented, loudly-labelled, auto-resetting user choice with a red warning. Adults
can consent. Removing it costs a feature.
*Dietitian:* consent does not survive a UI. The user who ticks it is not the user who eats the meal
three days later, and the whole safety story is "the weak path is unreachable" — an override makes
it reachable by design.
**Adjudication: Dietitian, unambiguously.** Remove it on web. The feature it protects — AI recipe
generation — is on the kill list anyway (Stage 5).

## STAGE FOUR — THE REBUILD

### Positioning

> **For the guy who already knows his macros and is sick of logging: Cut Protocol measures what your
> body actually burns from your weigh-ins alone, then tells you exactly what to eat and how much —
> so you stop weighing your chicken and start hitting your numbers.**

One sentence. Specific person (already tracks, hates logging), specific pain (the logging tax),
specific outcome (exact portions without the tax). It leads with the one capability a chat window
cannot have, and it does not mention BMR formulas, provenance, or a solver — because those are
reasons to *stay*, not reasons to *start*.

### Pricing

**Recommendation: $14.99/month or $119/year, with a 14-day free trial that requires a card.**

*Why $14.99:* the current $24.99's only job is to make $125/yr look like a 58% saving. That is a real
tactic, but it is fragile in exactly this situation — a prospect who won't risk $25 to *try* an
unknown app never reaches the annual. $14.99 sits between MacroFactor ($11.99) and MyFitnessPal
($19.99), which is a defensible premium for an unknown brand rather than a category high.

*Why $119/year:* holds "save 34% — four months free," lands just above MacroFactor's $71.99 and
below MyFitnessPal's $79.99 on a per-month basis ($9.92), and annual is where the money actually is
for a product whose users churn when the cut ends. **An annual plan converts a designed-in end date
into twelve months of revenue.** For this business that is the single most important pricing fact.

*Why 14 days, and why it is not arbitrary:* `expenditureEstimator` needs roughly two weeks of
weigh-ins before `adaptive.applied` flips true. **Ship the trial length that matches when the product
starts working.** A 7-day trial asks them to judge you before the differentiator has fired. The
entitlement code already handles `on_trial` → premium (`entitlement.js:23`) — zero new code.

*Margin check:* net of Lemon Squeezy's 5% + $0.50, $14.99 → $13.74/mo; $119 → $112.55/yr ($9.38/mo).
Against ≤$1.60/user LLM and $5–25/mo total infra, gross margin is ~88% and break-even is 3
subscribers.

**Alternatives modelled and rejected:**

| Option | Why rejected |
|---|---|
| **$9.99/mo flat** | Undercuts MacroFactor, signals commodity, and at ~90% margin the extra $5 is pure loss. Price is not the objection — trust is (Q5 #2). Cutting price to solve a trust problem just leaves you poor and still untrusted. |
| **Keep $24.99 + 7-day trial** | The premium is unsupportable without brand or reviews, and 7 days ends before the adaptive engine fires. You would be charging the most in the category for the least-known product and letting people evaluate it during the only window when it looks like everyone else. |
| **Lifetime deal ($199 one-time)** | Tempting for early cash and it does solve the churn-on-goal-completion problem. Rejected: it caps LTV permanently on your first and best customers, and support obligations are perpetual against zero recurring revenue. Revisit only if you need a cash injection to survive. |

### The retention architecture

Fires on the schedule in Q2. Mechanically:

- **A `SentMessage` table + a Railway cron service** (Railway supports scheduled services natively —
  no new infra). One nightly job: for each active user, evaluate day-index and state, send at most
  one email, record it. ~200 lines.
- **Resend** for delivery. Free tier is 3,000/month — more than enough for the first 100 users.
- **What they lose by leaving**, made explicit at day 30 and again in the cancel flow: the measured
  expenditure curve and its confidence band. Show it as a chart with the formula estimate as a flat
  dotted line and the measured value diverging from it. That one image is the entire product.
- **Where the app reaches out unprompted:** day 3 (no weigh-in yet), day 14 (adaptive on — the only
  celebratory message), weekly digest, and a stall-detection message when 3 weeks of data show
  weight flat despite adherence ("your burn dropped 180 — here's the new target, and why").
- **What must NOT fire:** streak shaming, notification spam, "you haven't logged in 3 days!" The
  constitution forbids engagement bait and it is right — this cohort will churn *harder* if you
  nag them. Every message must carry information, not guilt.

### The "can't live without it" spec

By week four the app must know four things no competitor knows about this person:

1. **Their measured expenditure with a confidence band** — MacroFactor knows this too. Table stakes.
2. **Their real adherence rate** (planned vs. actually-eaten) — MacroFactor cannot know this because
   it has no plan to diverge from.
3. **Which specific meals they actually ate versus skipped** — from `ate-as-planned` + diary.
4. **Therefore: a personal recipe pool of things they have demonstrably eaten**, and a solver that
   only ever plans from it.

**#4 is the "unthinkable to quit" mechanic and it is not built.** By week four the app should be
generating a week composed almost entirely of meals this person has already eaten and not skipped,
at portions that hit a target derived from their own measured burn. Leaving means going back to a
stranger's meal plan and a textbook's guess. That is a real switching cost, it compounds weekly, and
it is built from data you are *already collecting and throwing away.*

The wiring: `MealLog` + `PlanSlot` → an adherence score per recipe → feed it into `mealSolver`'s
existing **soft bias** layer (`recipeTaste.js` already has the seam; soft biases shape pick
probability without touching eligibility, so allergy and diet filters are structurally unaffected).
Estimated 16 hours. **This is the highest-value feature in the document.**

### The cheapest falsifiable test

**Not a landing page.** A landing page tests whether your copy is good. You already know the copy
problem is trust, and an email address from a stranger who has never seen the product is not
evidence of willingness to pay. It also produces zero information about the thing most likely to
kill you, which is day-30 retention.

**The test: 20 free accounts to strangers, one 14-day cycle.**

- One honest post in r/fitness30plus or r/leangains: construction worker, built this at night,
  here's what it does, 20 free accounts, I want to know if it's useful.
- Recruit 20. Onboard them. Do nothing else — no hand-holding, no concierge. You are measuring the
  product, not your enthusiasm.
- **Falsifiable metric: ≥6 of 20 open the app on day 14.** Below 6 and the retention problem is
  fatal in its current form and no amount of billing plumbing changes that.
- **Secondary metric: ≥10 of 20 log at least 3 weigh-ins.** Below that, the adaptive engine — your
  only real differentiator — never fires for most users and the positioning is dead.
- Cost: ~6 hours plus the Railway/Supabase free tiers. Zero dollars.
- It also produces the testimonials that a landing page would have needed.

**Alternative considered — 10-person concierge (you generate their week manually and send it as a
PDF).** Better at testing the *value prop* in isolation, and it removes every UI confound. Rejected
as the primary test because it removes the confound that matters: whether they will *use software*
on day 14 without you in the loop. Run it as a fallback if the 20-account test can't recruit.
