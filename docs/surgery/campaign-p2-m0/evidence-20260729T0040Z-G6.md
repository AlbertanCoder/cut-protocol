## The determination

**It is a test fixture. It is not key material.** Stated without re-quoting the
literal, since the value is already once in the record and `guard-bash` refuses
any command carrying it:

- The string after the vendor prefix is an **all-caps hyphenated English
  sentence** announcing itself as the upstream key that must never leak,
  roughly 50 characters, containing ordinary dictionary words.
- A genuine Anthropic key is the prefix plus on the order of 95 characters of
  high-entropy base64url. The autopsy record puts the real one in
  `backend/.env` at **length 108** (`docs/autopsy/autopsy-20260727-0126/`).

Length and character distribution decide this on their own. No trust in the
words is required, which is the point — a fixture that *claims* to be fake
proves nothing, but a fixture that is 50 characters of English cannot be a
108-character random key.

**G6 downgrades** from "undetermined, possible live secret" to "known fixture
tripping a scanner rule." It still fails `npm run scan:secrets`, so it still
blocks a clean push — but for a false-positive reason, and the fix is one line.

## Why this line trips and its sibling does not

`backend`'s other relay fixture, `relayEndToEnd.test.js:31`, holds a
structurally identical fake key and is **not** flagged.

The difference is not the value. It is the variable name.

`scanSecrets.mjs` skips any line matching `PLACEHOLDER` before running a single
rule. That sibling's variable is named `FAKE_UPSTREAM_KEY` — `fake_` is a
recognized placeholder token, so the whole line is skipped. The flagged line's
variable is named `REAL_KEY`, which contains no placeholder token, so it is
scanned and matches.

**The scanner is reading the variable name as evidence about the value.**

## G7 — NEW, and more serious than G6

`scanText()` applies `PLACEHOLDER` as a **line-level skip, before any rule
runs**:

    if (line.includes(ALLOW_MARK)) continue;
    if (PLACEHOLDER.test(line)) continue;
    for (const rule of RULES) { ... }

So **a genuine secret is invisible to the scanner if anything else on its line
matches the placeholder heuristic** — `example`, `sample`, `dummy`, `todo`,
`redacted`, `placeholder`, `xxxx`, `<a`, or a literal `...`.

A real key in a line such as `ANTHROPIC_API_KEY=<real> # example config` is
never examined. Not flagged and skipped — never examined.

This is the harness's own pathology, one directory over: an **allow**-heuristic
matched against arbitrary prose, deciding whether the **deny** rules get to run
at all. The false-negative direction is the dangerous one, and it is silent by
construction. `ALLOW_MARK` (`scan:allow`) already exists as the *deliberate*
declaration mechanism; `PLACEHOLDER` is the accidental one sitting beside it.

I have not verified whether any real secret currently hides this way — that
needs a scan run with `PLACEHOLDER` disabled, which is a code change to a file
off my manifest. **EXPECTED from code read, not OBSERVED.**

## Recommendations

**G6** — one line, and the mechanism is already declared: append `// scan:allow`
to `relay/test/relay.test.js:20`, or rename `REAL_KEY`. I cannot: `relay/` is
off-manifest and `guard-edit` refuses, correctly. Needs an order or the owner's
hand.

**G7** — narrow `PLACEHOLDER` so it can only suppress a finding when the token
sits *inside the matched value*, not anywhere on the line; or retire it in
favour of the explicit `scan:allow` marker, which is auditable. Then re-run with
it disabled once, to see what it has been hiding. That last run is the one worth
scheduling regardless of which fix is chosen.
